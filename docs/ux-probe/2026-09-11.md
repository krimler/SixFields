# UX probe, 2026-09-11

Run by: an agent given only docs/user-guide.md, README.md and ./bin/cluster.

## Result against thresholds

| threshold | target | actual | pass/fail |
|---|---|---|---|
| commands to a first correct status of a cluster | 3 | 3 | pass |
| commands to the stall reason, holding a stalled cluster | 2 | 1 | pass |
| commands to the stall reason, starting from no stalled cluster | not set | 4 | n/a |

The second threshold passes on its own terms. Reaching the point where it applies
took three further commands, because the flag that produces a stalled cluster is
absent from both documents I was given.

## Task 1, create a cluster

### Commands

1. `kubectl get clusterclass -A`, succeeded. Five classes: `std`, `std-hosted`,
   `std-inmemory`, `std-inmemory-stall`, `std-inmemory-vmstall`.
2. `./bin/cluster new probe-1 --version v1.34.11 --pool default=2 --class std-inmemory`
  , succeeded, printed the manifest on stdout. `--class` is a guess; see dead ends.
3. `./bin/cluster up probe-1 -f probe-1.yaml --no-tty --timeout 5m`, succeeded.
   `ready in 47s`, exit 0.
4. `./bin/cluster status probe-1`, succeeded, exit 0. Run after the threshold was
   already met, to confirm status reads the same outside `up`.

The manifest from step 2 was written to a scratch file between steps 2 and 3
without running another command.

### Time

15:34:18 to 15:35:27. 69 seconds, of which 47 were the cluster building.

### Dead ends

- README and the user guide both write the binary as bare `cluster`. It lives at
  `./bin/cluster` and is not on PATH. Every example has to be edited before it runs.
  This costs nothing after the first time, and it makes every copied line fail once.
- `cluster new` is shown once in each document, always as
  `cluster new dev-1 --version v1.34.11 --pool default=2`. Neither document lists
  its flags, and neither says how to select a class other than `std`. I guessed
  `--class std-inmemory`. It worked. Had it been `--class-ref` or `--clusterclass`
  the guess would have cost a command.
- The `size` and `placement` variables are documented as optional with defaults.
  `cluster new` emits both explicitly. The generated file is therefore larger than
  the six-field example the documents lead with.

### Where the answer came from

The manifest shape came from README "The order form" and the user guide "Six
fields". `cluster new` came from README line 83. `--no-tty` came from the user
guide, "What you'll see during the wait". The class name came from
`kubectl get clusterclass`. The `--class` flag came from a guess.

## Task 2, diagnose a stall

### Commands

1. `kubectl get clusters -A`, succeeded, and showed no stalled cluster. Only
   `probe-1`, already `Provisioned`.
2. `./bin/cluster --help`, succeeded, and showed no `replay` subcommand. Dead end.
3. `./bin/cluster status --help` and `./bin/cluster why --help`, succeeded, and
   showed `--replay string` on both, with the example
   `cluster why --replay testdata/fixtures/inmem-stall-vm`.
4. `./bin/cluster why --replay testdata/fixtures/inmem-stall-vm`, succeeded,
   exit 2. This is the answer.
5. `./bin/cluster why --replay testdata/fixtures/inmem-stall-vm --verbose`,
   succeeded, exit 2. Full ranking, 18 losing candidates listed with a reason each.
6. `./bin/cluster docs CAPI-CP-002`, succeeded, printed the runbook.

The answer:

```
DevMachine/mem-vmstall-k4ssg-rt7mf, a control-plane machine is stuck provisioning (5m25s)
raw: kubectl get devmachine.infrastructure.cluster.x-k8s.io mem-vmstall-k4ssg-rt7mf -n default -o yaml
next: cluster docs CAPI-CP-002
```

The blocking object is `DevMachine/mem-vmstall-k4ssg-rt7mf`. The condition is
`VMProvisioned=False reason=WaitingForStartupTimeout`. Everything else that is
False on that DevMachine waits on `VMProvisioned`, and everything on the Machine,
the KubeadmControlPlane and the Cluster is a less specific object. `--verbose`
states each of those two facts per losing candidate.

### Time

15:35:43 to 15:36:04. 21 seconds to the stall line. 28 seconds including the
ranking.

### Dead ends

- The brief for this probe said the user guide mentions replaying recorded runs
  from `testdata/fixtures/`. It does not. The string `replay` appears in the user
  guide zero times. It appears in README once, as `make replay F=inmem-stall-vm`,
  inside "Working on SixFields", which reads as a section for contributors. A user
  who stops reading at "Cleaning up" never learns the feature exists.
- `cluster --help` lists no replay subcommand, so the top-level help does not
  recover it either. `--replay` is a per-command flag, visible only from
  `cluster status --help` or `cluster why --help`.
- The usage line is `cluster why NAME [flags]`, and the example directly below it
  is `cluster why --replay testdata/fixtures/inmem-stall-vm` with no NAME. I had
  to guess that NAME is optional when `--replay` is given. It is.
- Both documents print a four-line stall block containing
  `typical: p50 1m15s · p95 2m00s`. The real output has three lines and no
  `typical:` line. The documented line is the one that separates slow from stuck,
  which is the judgement the section exists to support. I could not tell from the
  output whether 5m25s is abnormal for this phase.
- The fixture directory name had to be taken from a help example. There is no
  command that lists available fixtures, and the documents name only
  `inmem-stall-vm`. Two of the five installed ClusterClasses are named
  `std-inmemory-stall` and `std-inmemory-vmstall`, which suggests a live stall is
  also creatable, and no document says so.
- README calls rung 2 `cluster why dev-1 --verbose`; the user guide calls the same
  rung `cluster why dev-1 --explain-ranking` in one place and `--verbose` in
  another. Both flags exist. Nothing says whether they differ.

### Where the answer came from

`--replay` came from `cluster why --help`, from neither document. The fixture path
came from the same help example. Reading the output came from the user guide,
"What a stall looks like" and "Five rungs", both of which describe the format
accurately apart from the missing `typical:` line.

## Task 3, eject

### Commands

1. `./bin/cluster render probe-1 > probe-1-objects.yaml`, succeeded, exit 0.
   706 lines, 18 objects: Cluster, ClusterResourceSetBinding, DevCluster,
   3 DevMachines, 2 DevMachineTemplates, 3 KubeadmConfigs, KubeadmConfigTemplate,
   KubeadmControlPlane, 3 Machines, MachineDeployment, MachineSet.
2. `kubectl apply --dry-run=server -f probe-1-objects.yaml`, **failed**. 13 of the
   18 objects were rejected by `ValidatingAdmissionPolicy sixfields-managed-kinds`.
3. Same command, filtered, to count what passed, 5 objects dry-run applied
   (Cluster, ClusterResourceSetBinding, 3 DevMachines), 13 forbidden.
4. Read the rendered Cluster object out of the file, `spec.topology` is present.
5. `./bin/cluster render --help`, succeeded, and showed no flag that changes any
   of this. Its own help text repeats the claim that the output re-applies with no
   diff.
6. Read `docs/eject.md`, which the denial message named.

The file exists and is complete. The property the documents use to prove it is
complete does not hold.

### Time

6 seconds to the file, 15:38:44 to 15:38:50. A further 1m45s establishing that the
documented verification step fails, and reading `docs/eject.md` to find out why.

### Dead ends

- The verification step fails. README, the user guide, `docs/eject.md` and
  `cluster render --help` all state that
  `kubectl apply --dry-run=server -f <render output>` produces no diff, and the
  user guide annotates the line `# no diff`. Running it against a cluster this tool
  created 4 minutes earlier denies 13 of 18 objects. This is the one check a user
  is told to run to know the escape hatch worked, and it reports failure.
- The denial message names the wrong class:
  `Machine is managed by ClusterClass 'std'`. `probe-1` uses `std-inmemory`.
  `std` is hardcoded. A user with several classes installed will look at the wrong
  one.
- `docs/eject.md` line 121 says the render output is the computed topology "with
  `spec.topology` removed". The rendered Cluster still carries the full
  `spec.topology` block, and the `last-applied-configuration` annotation carries a
  second copy of it. A file that keeps `spec.topology` keeps the ClusterClass
  dependency the section is about removing.
- `cluster render` has one flag, `--replay`. There is no flag to strip topology, to
  skip the managed kinds, or to emit a form that applies. The message points at
  `docs/eject.md`, and the only remedy there is to delete the admission policy or
  to obtain a group membership from an identity provider. Neither is something a
  first-time user can do to check that their own eject worked.
- Every object also drew a warning about the missing
  `kubectl.kubernetes.io/last-applied-configuration` annotation. That is expected
  for server-side objects and is harmless, and it buries the five lines that
  succeeded under nineteen lines of warning.

### Where the answer came from

`cluster render` came from README "Leaving" and the user guide "How to eject", and
was correct and immediate. The verification command came from the user guide and
was wrong. The reason it was wrong came from `docs/eject.md`, which the tool's own
denial message named, and which repeats the same wrong claim two sections later.

## What was confusing

1. `kubectl apply --dry-run=server` on the render output fails. Four separate
   places promise an empty diff. The result is 13 forbidden objects. This cost the
   most time and is the only finding here that would make a user distrust the tool,
   because the failing check is the one offered as proof that they can leave.
2. `--replay` is undiscoverable from the two documents a user is given. It exists
   only in per-command help. Without the brief telling me replay existed I would
   have concluded there was no way to see a stall without waiting three minutes on
   a real one.
3. The admission denial names ClusterClass `std` for a cluster built from
   `std-inmemory`. The message is confident and wrong, and there were four other
   classes installed for it to be wrong about.
4. The stall line is missing the `typical: p50 … · p95 …` row that both documents
   show. The documents build a whole argument on that row separating slow from
   stuck, and then the tool does not print it.
5. `cluster new` has no documented flag list, so selecting a class was a guess.
6. `docs/eject.md` says `spec.topology` is removed from the render output. It is
   there twice, once in the spec and once inside the last-applied annotation.
7. Every documented invocation uses bare `cluster`, and the binary is at
   `./bin/cluster`.
8. `cluster why NAME [flags]` with an example that omits NAME.

## What worked without thinking

- `cluster new` → file → `cluster up` is three commands with no surprises. The
  generated manifest applied unchanged. Exit 0 at the end, and `ready in 47s`
  matched what `kubectl get clusters` reported.
- `--no-tty` did exactly what the user guide said: one line per state change, with
  `t+7s` style offsets, readable in a transcript. The phases arrived in the
  documented order, and the workers row stayed `running` behind the control plane
  without ever claiming to be the problem.
- `cluster why --replay …` gave the correct blocking object in one command, with
  the condition, the duration, a pasteable kubectl command, and the runbook code.
  Nothing in the line needed interpretation.
- `--verbose` answered the follow-up question before it was asked. Every one of the
  18 losing candidates has a stated reason: `waiting on VMProvisioned`,
  `summary condition`, `less specific object`. The ranking is legible without any
  knowledge of the codebase.
- `cluster docs CAPI-CP-002` printed a real runbook, ordered by the four steps of a
  Machine's life, and it named the adjacent codes (`CAPI-CP-001`, `CAPI-WRK-002`)
  and the condition that distinguishes them. It told me I was in the right runbook.
- Exit codes behaved as documented: 0 for ready, 2 for stalled. A script could act
  on these without parsing text.
- `cluster render` produced the 18 objects in 6 seconds, sorted, with the templates
  the generated objects came from. As an artifact to keep and read it is complete.
